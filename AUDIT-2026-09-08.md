# ArchPad independent milestone audit

Audited: **2026-09-08 IST**  
Auditor: **Codex**  
Scope: workspace artifacts, package sources, release manifests, recovery
artifacts, and read-only inspection of the running Xiaomi Pad 6.

This audit did not modify the tablet or existing project files. It is an
independent checkpoint for review by the owner and Antigravity before the
touch-first GUI phase continues.

## Executive assessment

The migration is real and technically significant. The tablet boots a genuine
native Arch Linux ARM aarch64 userspace with pacman, the source-built pipa
kernel, native device packages, a clean console baseline, and working hardware
enumeration. This is not an Alpine/postmarketOS root with Arch branding.

The project should nevertheless distinguish **a working native Arch hardware
prototype** from **a reliable, reproducible and safely updatable ArchPad
base**. `ROADMAP.md` currently labels Phase 3 complete, but several original
Phase 3 requirements remain open.

Approximate progress:

| Scope | Assessment |
|---|---:|
| Hardware-enablement foundation | ~90% |
| Native Arch console milestone | ~80% |
| Reliable/updatable Arch base | ~60% |
| Touch-first graphical environment | Not started |
| Complete original ArchPad vision | ~35--40% |

These percentages are directional engineering estimates, not measurements.

## Directly verified live state

The following was verified over read-only SSH against the running tablet:

- OS identifies as native **Arch Linux ARM**, `aarch64`, rolling release.
- Running kernel is `7.1.4-pipa`.
- All six native packages are installed:
  - `linux-archpad-pipa 7.1.4-7`
  - `archpad-pipa-firmware 1.0.0-1`
  - `archpad-pipa-device 1.0.0-1`
  - `archpad-pipa-audio 1.0.0-1`
  - `archpad-pipa-camera 1.0.0-1`
  - `archpad-boot 1.0.0-1`
- `pacman -Q` reports 326 packages.
- Default target is `multi-user.target`; no final GUI/compositor is installed.
- systemd reports zero failed units.
- Root is `/dev/loop0p2`, ext4, approximately 106 GiB, with about 2.6 GiB
  used.
- `/boot` is `/dev/loop0p1`, FAT, approximately 480 MiB.
- Idle memory use was approximately 469 MiB of 5.4 GiB.
- A 2.7 GiB zram swap device is active.
- USB CDC-NCM networking and SSH work.
- Adreno 650 acceleration is genuine:
  - Turnip/Mesa 26.2.2, Vulkan 1.3;
  - Freedreno FD650, OpenGL 4.6 and OpenGL ES 3.2.
- ALSA exposes the Xiaomi Pad 6 playback and capture PCMs.
- QCA6390 Wi-Fi enumerates with `ath11k_pci`; `iwd` is active.
- Bluetooth `hci0` is initialized and powered.
- Novatek touchscreen and pressure/tilt pen input devices enumerate.
- Battery capacity, voltage and current are reported through `qcom-battery`.
- Both camera sensors enumerate in libcamera:
  - rear OV13B10;
  - front HI846W on two CSI-2 lanes.
- HI846 loads `/usr/share/libcamera/ipa/simple/hi846.yaml`.
- The six custom packages report no missing installed files.

Functional tests already documented by the project, such as speaker playback,
microphone capture, touch/pen event testing, Wi-Fi scanning, Bluetooth
scanning and brightness control, are credible and consistent with the live
enumeration. This audit did not repeat disruptive, audible, interactive or
suspend tests.

## Confirmed boot and storage chain

The live system proves the following chain:

```text
Qualcomm ROM
  -> Xiaomi firmware and ABL fastboot
  -> boot_a containing pipa U-Boot
  -> U-Boot exposes UEFI services
  -> systemd-boot from the nested EFI System Partition
  -> Image + initramfs + Tianma DTB
  -> Arch root on /dev/loop0p2 inside Android userdata
```

Live `bootctl` reports the firmware as:

```text
UEFI 2.110 (Das U-Boot 8230.4096)
```

The essential verified fact is that the firmware is **Das U-Boot** and the
current loader is **systemd-boot 261.2-1-arch**. The odd numeric firmware
version is U-Boot's reported UEFI version and does not imply Android is loading
the kernel directly.

The active entry loads:

```text
/Image
/initramfs-linux.img
/dtbs/qcom/sm8250-xiaomi-pipa-tianma.dtb
root=UUID=c6e69b4d-faec-48bf-9df7-6083807d27cb
cma=128M
```

Current `boot_a` SHA-256:

```text
166829a72d63e4304d37336a51a0c5e24fb379b365eee81681f2af5008c38d85
```

This exactly matches the decompressed known-good `boot_a` in the postmarketOS
backup. The corrected U-Boot description in `HANDOFF-ANTIGRAVITY.md` now
agrees with live evidence.

## Strong implementation choices

### Native package boundaries

Separating kernel, firmware, device policy, audio, camera and boot integration
is aligned with the original design. It permits each hardware layer to evolve
through pacman rather than accumulating untracked live edits.

### Native kernel package

`linux-archpad-pipa` is a real AArch64 pacman package built from upstream Linux
7.1.4 plus the checksummed pipa patch stack. The retained package checksum
passes. Its payload includes:

- kernel Image;
- Tianma DTB;
- `7.1.4-pipa` module tree;
- kernel configuration and System.map.

The project records 585 modules, matching vermagic and the two-lane HI846 DTB.

### Firmware and device data

The firmware package contains the relevant Adreno, ADSP, CDSP, SLPI, Venus,
Novatek, Awinic and Nuvolta blobs plus the Qualcomm sensor registry. It is
packaged natively rather than installing Alpine APK contents into the Arch
root.

### Recovery backup

`artifacts/private/tablet-backup-postmarketos-2026-09-07/` contains the
postmarketOS root, ESP, boot partitions, selected device partitions, firmware,
audio/camera data and partition-layout records. Every entry in its SHA-256
manifest passed verification during this audit.

### Clean baseline

Removing temporary Plasma and Phosh experiments before selecting the final
shell was a good architectural reset. The current 326-package console system
is small and leaves almost all RAM and storage available.

## Findings requiring resolution

### P1: source state and image assembly are not reproducible yet

The project directory is not currently a Git repository. There is therefore no
authoritative commit for the package sources or a reviewable history of the
Arch migration.

The host-side commands that created the 4K-sector nested GPT, ext4 root, ESP
and Android sparse image are also not preserved as an executable build script
in the clean project tree. `ROADMAP.md` says the image builder is complete, but
only the runtime initramfs mapping hook is present under `packages/archpad-boot`.

The original `archpad-root.img` and `archpad-userdata-sparse.img` were removed
during cleanup. Removing large generated outputs is reasonable only after the
complete release can be regenerated from versioned scripts and inputs.

Recommended acceptance condition:

1. version all authoritative text/source inputs;
2. add a non-interactive image builder;
3. build twice from a clean state;
4. compare package/image outputs or explicitly document unavoidable variance.

### P1: retained release manifest is inconsistent

`artifacts/private/archpad-release/SHA256SUMS` records this ESP hash:

```text
560785b8c94ef57646c4495524c12bebc572519db914278af37d1b6c72e890d4
```

The retained `archpad-esp.img` currently hashes to:

```text
b4c0b1be6ad978b3cb8e21a86958df0447b0b168f469013fea2f729983cf57de
```

The rootfs archive passes its hash. The manifest also lists the deleted root
and sparse images. This does not damage the installed tablet, but the retained
release set cannot currently pass its own verification.

### P1: kernel build reproducibility is unproven

The kernel config enables signing of all modules while using a generated key.
The installed HI846 module reports:

```text
signer: Build time autogenerated kernel key
```

The build tree contains the generated private key. A clean rebuild will create
a different key and therefore different modules/package bytes. Signature
enforcement is disabled, so these signatures currently provide no enforced
trust boundary.

Only one final package was retained; no two-clean-build comparison is recorded.
No detached signatures exist for the pacman packages.

A deliberate policy is needed: disable automatic module signing during the
reproducible development phase, or establish a properly managed release key
and document which artifacts are expected to vary.

### P1: kernel updates are not yet safe or atomic

The current kernel package installs `/boot/Image`, the DTB and modules, but no
complete pacman/ALPM deployment hook was found that guarantees:

- matching initramfs regeneration;
- kernel, DTB, modules and initramfs consistency;
- preservation of the previous working kernel;
- validation before changing the default boot entry;
- rollback after a failed boot.

The system currently has one ArchPad boot entry. The postmarketOS backup gives
external disaster recovery, but there is no convenient on-device
current/previous rollback path.

### P1: system time is invalid

At audit time the tablet reported:

```text
1972-12-21
System clock synchronized: no
Time zone: UTC
```

NTP is enabled, but Wi-Fi was disconnected and USB networking did not provide
working upstream DNS. Invalid time can break TLS, pacman, browsers, tokens,
logs and build timestamps. ArchPad needs a reliable boot-time clock strategy
and correct timezone handling before normal online use.

### P1/P2: audio works but is not a reliable final implementation

Audio still depends on `archpad-audio-reprobe.service`, which unloads and
reloads the VA-macro module if the ALSA card is absent. This is a bounded and
understandable workaround, but the original plan calls for fixing the kernel
probe-order problem.

The current boot journal contained approximately 8,793 Awinic amplifier
failure/error lines, SoundWire port mismatch messages and a WirePlumber mixer
error. Repeated prior tests may inflate the count, but the volume is too high
to dismiss without classification.

The service also points to
`/usr/local/share/doc/archpad/audio-reprobe.txt`, while the package does not
install that document.

### P2: cameras are enabled, not fully integrated

Both cameras enumerate and the HI846 two-lane probe succeeds. The front-camera
hardware-enablement milestone is valid.

Remaining live libcamera warnings include:

- incomplete OV13B10 crop/selection API support;
- no OV13B10 static properties or sensor helper;
- no rear tuning file, falling back to `uncalibrated.yaml`;
- no HI846 sensor helper;
- minimal HI846 YAML containing generic BlackLevel/AWB/Adjust/AGC only.

Rear orientation, autofocus and image processing remain open. This audit
confirmed current Arch enumeration but did not perform fresh camera streaming.
A short bounded front/rear capture should be part of the Arch baseline gate.

### P2: unresolved kernel errors need triage

The live boot contains non-fatal but unresolved errors/warnings including:

- four DSI PLL lock failures before display recovery;
- failure to register the GPU cooling device;
- failed `bq25980-charger` probe;
- missing requested `crypto_user` module;
- Qualcomm remoteproc handover warnings;
- an I2C timeout during Nanosic keyboard-cover initialization;
- BPF metadata errors;
- SoundWire and amplifier failures.

Each should be classified as harmless startup noise, configuration error or a
real reliability/power-management defect. They do not invalidate the successful
Arch boot or GPU/camera enumeration.

### P2: the retained rootfs is not the exact current baseline

The retained Arch rootfs archive contains approximately 170 package database
entries, while the cleaned live system contains 326 packages. The live system
is therefore ahead of that archive. Capture a sanitized package/configuration
manifest of the exact console milestone before GUI changes.

### P2: private rootfs contains development secrets

The retained rootfs archive contains SSH host private keys, `/etc/shadow` and
an authorized key. The owner has explicitly accepted agent access to temporary
development credentials to keep development seamless. This is **not a current
development blocker**.

Required boundary:

- keep secret-bearing artifacts ignored under `artifacts/private`;
- never publish or upload them;
- generate unique SSH host keys on first boot for distributable images;
- rotate/remove passwords, authorized keys and temporary credentials before
  daily use or release.

### P3: minor packaging hygiene

- Package URLs point generally to `https://github.com/pipa-mainline` rather
  than an exact ArchPad source repository/ref.
- The custom packages are currently unsigned.
- The project should install applicable license/provenance files in packages.
- The minimal camera YAML should be described as a bring-up profile, not
  complete sensor tuning.

## Recommended gate before final GUI construction

Create a short **Phase 3.5: baseline hardening** milestone:

1. reconcile `ROADMAP.md` and this audit;
2. version the authoritative project sources;
3. preserve the complete image builder and release manifest generator;
4. regenerate or formally supersede the stale release manifest;
5. choose the module/package signing and reproducibility policy;
6. perform two clean kernel/package builds and compare them;
7. implement an atomic kernel deployment hook and previous-kernel entry;
8. fix the clock/NTP strategy;
9. capture the exact current package/configuration manifest;
10. run bounded Arch smoke tests for both camera streams, keyboard cover,
    sensors, charging and suspend/resume;
11. triage the DSI, GPU cooling, charger and audio errors.

This need not delay all GUI experimentation. A compositor prototype can be
tested in parallel conceptually, but it should not be declared the ArchPad
baseline or layered with extensive customization until the boot/update and
reproducibility gates are resolved.

After the hardening gate, the planned order remains:

```text
Wayland compositor
  -> login and PAM lock security
  -> scaling
  -> rotation plus touch/pen mapping
  -> automatic OSK
  -> gestures
  -> keyboard-cover-aware behaviour
  -> Quickshell/custom ArchPad shell
  -> tablet applications
  -> voice improvements
  -> AI/Gemini last
```

## Questions for Antigravity

Antigravity should answer these from its session history and any evidence that
was intentionally removed during cleanup:

1. What exact commands or scripts created the nested GPT, ESP, ext4 root and
   Android sparse userdata image? Can they be reconstructed as one versioned,
   non-interactive builder?
2. Why was `archpad-esp.img` modified after `SHA256SUMS` was written? What
   changed between hashes `560785...` and `b4c0b1...`?
3. Were two clean kernel builds compared? If so, where is the evidence, and
   how was the autogenerated module-signing key handled?
4. What exact procedure is intended for a normal pacman kernel update? What
   regenerates the initramfs, preserves the old kernel and activates rollback?
5. Were front and rear **streams**, not merely enumeration, tested under the
   current native Arch installation? Record the commands and results.
6. Was suspend/resume tested after the final console cleanup and with the
   current kernel/initramfs?
7. What produced the very large Awinic amplifier error count, and are errors
   still accumulating while the system is idle?
8. What clock strategy was planned (network time, persisted software clock,
   RTC correction, or a combination)?
9. Is the `aur` pacman repository intentionally trusted, and what repository
   supplies it?
10. Which current live-system changes are not represented in the retained
    170-package rootfs archive or package sources?
11. What evidence supports calling Phase 3 complete rather than moving the
    remaining items into a Phase 3.5 hardening gate?

## Bottom line

The hardest conceptual milestone has been crossed: ArchPad now has a real,
fast, minimal Arch Linux ARM system running on Xiaomi Pad 6 hardware. The work
is promising and sensibly separated into native packages. It is presently a
strong engineering prototype, not yet a reproducible or safely updatable base.
A focused hardening checkpoint will prevent the touch interface from being
built on hidden boot, update and recovery weaknesses.
